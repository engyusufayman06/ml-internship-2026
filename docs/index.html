Which Content Should Be Reviewed First?

A practical, evidence-first workflow for prioritizing potentially declining content without turning a model score into an automatic decision.

Abstract

This project asks how a content team can prioritize pages for review when the goal is to surface potentially declining content without leaking the outcome into the model. I used the FlyRank internship content snapshot and treated trend_direction/trend_pct as evaluation-only signals rather than features. The final workflow uses a logistic-regression classifier with median imputation, missingness indicators, categorical one-hot encoding, and a client-grouped 80/20 holdout so a client does not appear in both training and test data. On the executed grouped holdout, the model reached 77.2% recall, 73.4% precision, 75.2% F1, and 0.838 ROC-AUC. The practical result is a ranked, human-reviewed queue—not an automatic refresh or deletion system—and the evidence should be treated as directional rather than causal or guaranteed to generalize to future clients.

Introduction / Problem

The operational question is simple: which pages deserve human attention first?

A naive rule can look attractive: wait until a page is old, then prioritize pages that still have meaningful visibility. That is useful as a baseline, but it can miss newer pages that the model considers worth investigating and it gives no probability-like ranking across the broader content set.

This work turns the question into a binary classification and prioritization problem. A positive case represents content labeled as declining; the model is used to order review candidates, while the final decision stays with a human.

What was excluded

  • trend_direction and trend_pct: these are directly tied to the decline outcome and would leak the answer.
  • is_declining_label: outcome only, never a feature.
  • content_id and client_id: identifiers/grouping fields, not predictive features.
  • Week-4 derived fields such as score, reason_code, action_label, freshness buckets, and volume buckets: derived from the baseline workflow and therefore excluded from the model feature set.
Public-safety rule: this page contains no client names, private search queries, or private URLs. IDs remain pseudonymized and are not used as predictive features.

Methodology

Features and preprocessing

  • Numeric features: median imputation + missingness indicators + standardization.
  • Categorical features: most-frequent imputation + one-hot encoding.
  • Model: logistic regression with class_weight="balanced", max_iter=1000, seed 42.
  • Decision threshold for classification: 0.50; ranking uses predicted probability.

Label

The executed workflow uses is_declining_label when available. When the starter export lacks that column, trend_direction == "down" is created as an evaluation-only proxy; it is never included in the feature matrix.

Validation design

The final validation is a client-grouped 80/20 split using GroupShuffleSplit with seed 42. This is stricter than a random row split because it prevents the same client from appearing on both sides of the evaluation.

Metrics

Recall is the primary decision metric because missing a genuinely declining page can be costly for a review queue. Precision, F1, ROC-AUC, and Precision@K are supporting measures.

Leakage check

The feature list explicitly removes target, target-derived fields, IDs, and baseline-derived fields. The notebook asserts zero client overlap on the grouped holdout and prints a leakage audit.

Baseline rule

The Week-4 baseline flags a page when it is at least 180 days since its last update and has at least 3,000 impressions in 90 days. On the 30,000-row starter snapshot, this rule flagged 9 pages for refresh review.

The baseline is intentionally simple and interpretable: its score is 90-day impressions for flagged pages and zero otherwise.

Same-split baseline honesty: the public starter export used for the baseline execution did not contain the decline label, so a retrospective baseline metric table on the grouped holdout was not available from the committed execution. I do not invent those numbers. The model metrics above are measured; the baseline comparison is therefore reported as the operational rule and its 9-page full-snapshot queue, not as a fabricated same-split score.

Limitations & honest framing

  • Not causal: the model finds associations useful for prioritization; it does not prove that changing a page will cause recovery.
  • Evaluation proxy: in the starter snapshot, the target may be reconstructed from trend direction for evaluation only. This is not a production label pipeline.
  • Client generalization: grouped validation is safer than row-random validation, but one 80/20 split is not evidence of universal future performance.
  • Baseline comparison: the committed baseline execution lacked the target column, so its retrospective metrics were not fabricated.
  • Ranking is not certainty: a high review score means earlier investigation, not a guaranteed decline.
  • Operational use: this is a practical internship research artifact, not a production decision engine.
Claim I am willing to make: on the evaluated client-grouped holdout, the available signals supported a measurable decline-risk ranking with 77.2% recall, 73.4% precision, 75.2% F1, and 0.838 ROC-AUC. The result is directional evidence for human review prioritization, not proof of causality or guaranteed future performance.
